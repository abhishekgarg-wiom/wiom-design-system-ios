# Chat copy guidelines for the customer app

Status: draft, adapted from the supplied customer chat guidelines. The recorded rendering precedent is basic native bubbles (13 Aug 2026). Product principles in [customer-adoption-doctrine.md](customer-adoption-doctrine.md) and terms in [glossary.md](glossary.md) retain their documented status. These guidelines do not assert that a proposed chat state is implemented today.

## Purpose and permitted jobs

Chat reduces uncertainty and helps the customer take the next step. It is not a sales, education, feature-explanation or brand-storytelling surface. Each message does one job:

- Confirm a state the system actually recorded.
- Name one next action, who performs it and when.
- Reduce anxiety with an operationally true explanation of a delay, failure or recovery.

A message doing none of these has no place in the thread. Do not pitch plans, compare speeds, repeat brand pillars, upsell, invent urgency or use superlatives. Offers and reward explanations belong on their dedicated surfaces. A factual acknowledgement of an earned reward is allowed when relevant, with no sales pressure.

## State and reading order

Pinned context carries current system truth. Chat explains changes or exceptions; a human support reply inherits the same facts. Neither may contradict the pin. Correct stale state instead of writing around it. Do not repeat the complete pinned status in every bubble.

Author each message for a named state:

| State | Message job | Avoid |
|---|---|---|
| Post-payment, pre-assignment | Confirm received payment and the honest next event and time window | Celebration, marketing, silence |
| Assignment confirmed | Say who comes, when and what happens next | New commercial information |
| Installation day | Logistics, access and what to have ready | Product lessons or recharge pitches |
| First days after install | Confirm normal operation and how to get help | Manufactured delight |


## Copy and rendering

Use Hindi and English as the surface requires, concise and precise. Say रिचार्ज, नेट and घर का नेट per the glossary. Prefer सिर्फ in chat and स्टेटस for casual UI. Real strings come from the catalog; examples are illustrative.

An in-thread action reads as the customer's next reply, first person where natural. Render messages as plain native bubbles with optional supplied hero image, timestamp, and an optional subtle text link separated by a divider. Do not put a filled screen CTA, promo card, gradient, shine, shimmer or wobble inside a bubble. Reward reveals and celebration treatments belong on dedicated surfaces reached through the text link. Screen CTAs still follow `wiom-ios-cta`; in-thread reply links follow this paragraph.

Before using a message, check all five:

1. It reduces uncertainty.
2. It reflects verified system state.
3. It creates no obligation or pressure.
4. It cannot reasonably read as a sales push.
5. The customer can explain what happens next.


The three draft state extensions and their open questions are preserved in [drafts-not-in-use.md](drafts-not-in-use.md), not in use. Agents must never load that file for screen or copy work. Verify a backend state before describing it as a fact.
